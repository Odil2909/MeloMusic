# Music API evaluation

**Checked:** 2026-10-19  
**Scope:** API and browser playback suitability for a public music service. This is a technical and terms review, not legal advice.

## Decision

There is no provider among the reviewed APIs that can be approved as the backend for the proposed commercial, general-catalog streaming service based only on public API access.

- **Apple Music is the strongest technical web player candidate** for a service that acts as a client for each listener's Apple Music subscription. MusicKit on the Web supports catalog search and browser playback. It is available in Uzbekistan. However, Apple says MusicKit must facilitate access to the end user's Apple Music subscription, prohibits monetizing that access, and prohibits downloading or modifying MusicKit content. It therefore does not grant the project a general-purpose audio catalog or the right to sell its own access to those recordings.
- **Jamendo is the best isolated technical prototype candidate.** Its API explicitly returns a stream field and supports searchable tracks, album tracks, artists, covers, durations, and genre tags. The read API is free for non-commercial use under its published API terms. A commercial project, including advertising-supported use, must contact Jamendo for a quote; individual tracks also carry their own Creative Commons license. Neither a returned `audio` URL nor an API client ID supplies blanket rights for a commercial streaming service.
- **Spotify is not suitable for this product.** Full playback uses the Web Playback SDK and requires Spotify Premium users. Spotify's policy says Streaming SDAs are only for Premium subscribers and commercial uses of Streaming SDAs are not permitted (including selling access or running ads on the app). Its API is suitable for metadata and linking, subject to policy and attribution, but metadata and previews do not make a streaming catalog.
- **SoundCloud is also not suitable as the aggregated catalog.** Its API can return playable streams and supports custom controls, but the API terms prohibit an alternative on-demand service aggregating user tracks; commercial use is restricted to narrow creator-focused cases. SoundCloud's own terms also prohibit using its player to create a new streaming service.

**Recommended next decision:** first choose the business model. For a paid/ad-supported service with its own accounts and playlists, obtain a written catalog/streaming agreement that explicitly covers interactive on-demand playback, territories including Uzbekistan, and the intended monetization. A music API is not itself that agreement. For a listener-owned subscription companion, evaluate Apple MusicKit separately and design around its restrictions. Jamendo is a useful sandbox for validating the technical flow, not a production recommendation until Jamendo confirms the exact service and rights in writing.

## Candidate notes

### Apple Music / MusicKit on the Web

Apple is the cleanest technical path for catalog playback inside a browser. Public catalog search can be made with a developer token; user-specific data and subscription playback involve user authorization/token handling. MusicKit on the Web manages the Music User Token for web applications. The developer token is signed using a private key; keep signing material server-side and issue only the appropriately scoped developer token to the client. [Apple MusicKit](https://developer.apple.com/musickit/), [user authentication](https://developer.apple.com/documentation/applemusicapi/user-authentication-for-musickit).

Apple's terms matter to the product design: do not charge or indirectly monetize access to the Apple Music service; enable full songs if playback is offered; let users initiate playback and use standard playback controls; do not download, upload, modify, or use the content outside the permitted MusicKit rendering. This is a subscription companion integration, not a license to rebroadcast Apple's catalog from the project's own stream server. Apple Music itself is listed as available in Uzbekistan, though individual recordings and a listener's subscription status still matter.

### Jamendo

Jamendo documents a catalog of roughly half a million tracks, read methods for tracks/albums/artists, track durations and images, genre tags, and a stream URL field. Track results expose a `license_ccurl`; the documentation examples include different Creative Commons terms, including non-commercial variants. Do not infer a uniform license from the fact a track is in the API. The API also has a `prolicensing` filter for tracks enrolled in its single-track commercial licensing program, but that filter by itself does not prove that a license covers this specific interactive streaming service, all territories, the desired monetization, or all underlying rights. [Track docs](https://developer.jamendo.com/v3.0/tracks).

Jamendo's API terms permit free non-commercial API use, but define advertising and other monetary advantage as commercial use and direct developers to licensing for a quote. They forbid designing an app to cache content or provide offline access, allow only operationally necessary caching, and require creator attribution plus a direct item backlink. The terms page says it was last modified in 2013; treat it as the published starting point and get current written terms for any commercial project. [API terms](https://devportal.jamendo.com/api_terms_of_use), [authentication and usage thresholds](https://developer.jamendo.com/v3.0/authentication).

**Inference:** Jamendo's independent/CC-oriented catalog is useful for a licensed prototype and discovery product but should not be assumed equivalent in coverage to a mainstream subscription catalog. The reviewed materials do not confirm every track is full length, streamable in Uzbekistan, or licensed for the proposed business model.

### Spotify

Spotify is a strong metadata source but not an own-brand commercial streaming backend. The Web Playback SDK creates a browser playback device and accepts an OAuth token for a Premium user; the Spotify guide explicitly requires Premium. Spotify's platform policy restricts streaming to Premium subscribers and prohibits commercial use of Streaming SDAs, including monetizing access or putting ads on the streaming app. Audio preview clips are sometimes absent, limited to 30 seconds when present, promotional only, and require a Spotify link. A returned metadata or external URL is not an audio source.

As of this review, development-mode apps require the owner to have Spotify Premium and are limited to five users. The July 2026 update increased client IDs to 25 per developer account and pools development quota at the account level. Search result `limit` maximum is 10 in the February 2026 migration. Wider access is not an automatic upgrade: Spotify's quota-mode review requires an eligible organization and a launched service, and the product remains subject to streaming policy. [Web Playback SDK](https://developer.spotify.com/documentation/web-playback-sdk), [policy](https://developer.spotify.com/policy), [development quota](https://developer.spotify.com/documentation/web-api/concepts/quota-modes), [July update](https://developer.spotify.com/blog/2026-07-23-web-api-quota-updates).

### SoundCloud

The API distinguishes playable, preview and blocked tracks; its guide describes public-stream access and the Widget API supports browser playback control. The same sources and terms make it a poor source for this product: SoundCloud API terms prohibit alternative on-demand services aggregating tracks from multiple users, do not permit SoundCloud Go content without a separate written agreement, require attribution/backlinks and only allow session-based caching. Its terms permit only narrow commercial API scenarios such as a creator delivering their own content to their own ad-enabled site. [API guide](https://developers.soundcloud.com/docs/api/guide), [API terms](https://developers.soundcloud.com/docs/api/terms-of-use), [Widget API](https://developers.soundcloud.com/docs/api/html5-widget).

## Playback, licensing and market conclusion

1. **No catalog API response is proof of a usable recording.** The candidate can disappear, be region-blocked, expose only a preview, require subscription authorization, or carry a license incompatible with the use. Confirm a representative sample only after the provider confirms rights and test actual playback for each relevant access path.
2. **A commercial service needs explicit rights for the exact product.** Ask the licensor to confirm in writing: interactive on-demand streaming; commercial model (paid subscription, advertising, or both); countries including Uzbekistan; web/mobile browser delivery; track/album artwork and metadata use; caching; user-created playlists/favorites/history; takedown and territory changes; and whether master and composition rights are covered.
3. **Realistic route:** obtain a direct license or an explicitly licensed B2B/white-label catalog contract. A metadata API may be used only where its terms allow, and the audio source must be independently licensed. Do not join a provider's metadata to a different provider's audio unless both sets of terms expressly allow that use.

## Selection for this stage

Jamendo was selected only for a **technical smoke-test harness**, because it is the one reviewed candidate whose public docs directly expose a stream field in read-only results and a documented test client ID. This does not select Jamendo for production. The technical API check could not complete in this execution environment (DNS to `api.jamendo.com` failed); no successful response or actual playback is claimed. The harness lets the developer repeat the API test on a machine with network access and test an individual track in a browser.

## Questions to resolve before stage 2

- Which business model is intended: paid subscription, ads, free/non-commercial, or subscription companion for an existing music service?
- Can the project obtain a written interactive streaming agreement for Uzbekistan and the intended territories/business model?
- Are Jamendo's current API terms and any per-track licenses suitable after a direct conversation with its licensing team?
- Which browser/device matrix and minimum catalog coverage are required?
- What is the approved policy for metadata persistence, artwork, takedowns, and territory-specific catalog filtering?
